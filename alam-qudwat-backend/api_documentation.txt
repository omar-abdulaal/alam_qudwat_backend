================================================================================
ALAM QUDWAT — BACKEND API DOCUMENTATION
================================================================================

Grounded, citable storytelling chat API over the Rashidun-caliphs RAG
knowledge base (see docs/RAG.md for the RAG pipeline itself). This backend
is the layer the Flutter app talks to; it never talks to the RAG database
directly from the client.

--------------------------------------------------------------------------------
1. ARCHITECTURE OVERVIEW
--------------------------------------------------------------------------------

Flutter app
    |  HTTPS + "Authorization: Bearer <API_AUTH_TOKEN>"
    v
FastAPI backend (app/)
    |  asyncio.to_thread(...) for the sync pieces below
    v
rag.retrieval.retriever.retrieve()   <- semantic search + metadata filter (unchanged)
    |
rag.generation.prompt.build_chat_messages()  <- grounded, narrator-mode prompt (unchanged core + new chat variant)
    |
app.services.llm.OpenAIChatLLM.stream()      <- the actual LLM call (new; rag/ deliberately has none)
    |
Server-Sent Events streamed back to the client, then the assistant turn +
citations (+ suggestions, if any) are persisted to Postgres
(app.db.models: conversations/messages)

Two separate SQLAlchemy DeclarativeBases share one Postgres database:
  - rag.db.models.Base   -> documents, chunks (RAG domain, untouched by this phase)
  - app.db.models.AppBase -> characters, categories, character_categories,
    conversations, messages, story_of_day
Both are migrated through the same Alembic history (alembic/versions/).

Voice I/O runs alongside chat, decoupled from it:
  - POST /api/v1/stt/transcribe: audio upload -> app.services.stt.OpenAISTT
    (OpenAI gpt-4o-mini-transcribe) -> plain transcribed text, no chat turn
    created. The client sends that text through POST /chat/stream itself.
  - POST /api/v1/tts/speak: text (or an existing message_id) ->
    app.services.tts.SilmaSageMakerTTS (the org's own SILMA model on AWS
    SageMaker, NOT OpenAI) -> streamed raw PCM audio.

--------------------------------------------------------------------------------
2. AUTHENTICATION
--------------------------------------------------------------------------------

Every /api/v1/* endpoint requires:

    Authorization: Bearer <API_AUTH_TOKEN>

<API_AUTH_TOKEN> is a shared secret configured via the API_AUTH_TOKEN
environment variable. This is the ONLY access control in this MVP phase —
there is no per-user account system yet (see Limitations, section 8).
Missing or wrong token -> 401 Unauthorized, JSON body {"detail": "..."}.

GET /health is intentionally NOT authenticated (for load balancer /
container orchestrator health checks).

The Flutter app must never embed the OpenAI key or the database
credentials — only this single API_AUTH_TOKEN, which grants access to the
backend's own endpoints, nothing else.

--------------------------------------------------------------------------------
3. ENDPOINTS
--------------------------------------------------------------------------------

GET /health
    No auth required.
    200 -> {"status": "ok"}   (also verifies DB connectivity)


GET /api/v1/characters
    Query params (optional):
      era       exact match on the historical period, e.g. "الخلافة الراشدة"
      group     exact match on the broad historical grouping, e.g. "الصحابة"
                or "الخلفاء الراشدون" (see the field notes below — distinct
                from "category")
      category  matches characters that have this one specific role among
                their (possibly several) roles, e.g. "خليفة" or "فقيه"
    200 -> array of Character:
        {
          "slug": "abu_bakr",
          "name_ar": "أبو بكر الصديق",
          "era": "الخلافة الراشدة",
          "group": "الخلفاء الراشدون",
          "categories": ["خليفة"],
          "short_description": "...",
          "avatar_url": null,
          "sort_order": 1,
          "created_at": "2026-08-09T19:32:17+03:00"
        }
    "era"/"group" are broad historical classification, set only by data
    seeding/migrations — never written by the AI classification script.
    "categories" is a controlled, multi-valued list of specific roles
    (from a fixed taxonomy: "خليفة", "أمير", "قائد عسكري", "فقيه", "محدث",
    "عالم", "طبيب", ... — see scripts/generate_character_classification.py
    for the full list) assigned by that script; a character can have zero,
    one, or several. Expect an empty array until that script has run for
    a given character — treat it as optional/progressively-populated data,
    not as always present.
    Only is_active=true characters are returned, ordered by sort_order.


GET /api/v1/characters/{slug}
    200 -> a single Character (same shape as above)
    404 -> unknown or inactive slug


GET /api/v1/story-of-day
    Query params (optional): date (YYYY-MM-DD, defaults to today, server time)
    200 -> StoryOfDay:
        {
          "story_date": "2026-08-09",
          "character": { ...Character... },
          "title": null,
          "teaser": null,
          "is_curated": false
        }
    Resolution: looks for a manually-curated `story_of_day` row for that
    date first (is_curated=true, with optional title/teaser); if none
    exists, deterministically rotates through active characters keyed by
    a hash of the date (is_curated=false) — no write happens for the
    default path, entirely server-computed, zero coupling to the client.


GET /api/v1/conversations/{conversation_id}
    200 -> Conversation with its full message history:
        {
          "id": "uuid",
          "character_slug": "abu_bakr",
          "narrator_mode": "adults",
          "created_at": "...",
          "updated_at": "...",
          "messages": [
            {
              "id": "uuid",
              "role": "user",
              "content": "...",
              "citations": null,
              "extra": null,
              "created_at": "..."
            },
            {
              "id": "uuid",
              "role": "assistant",
              "content": "...",
              "citations": [ {...Citation...}, ... ],
              "extra": {
                "suggestions": ["سؤال متابعة أول؟", "..."],   // omitted if none
                "diacritized_content": "..."                    // see below; internal use, ignore in the UI
              },  // or null
              "created_at": "..."
            }
          ]
        }
        `extra.diacritized_content`, when present, is the same answer
        with full Arabic tashkeel — kept only so POST /api/v1/tts/speak
        can synthesize speech for this exact message without a second LLM
        call (section 3, TTS). It is NOT meant to be rendered — `content`
        (no diacritics) is what the UI should always display; there is no
        reason for the Flutter app to read this field at all.
    404 -> unknown conversation_id
    Note: this endpoint exists so the Flutter app can resume a
    conversation after an app restart by persisting only the
    conversation_id locally (see section 5 — conversational continuity).


POST /api/v1/chat/stream   <-- THE MAIN ENDPOINT
    Content-Type: application/json
    Request body (ChatRequest):
        {
          "message": "كيف تولى أبو بكر الخلافة؟",   // required, non-empty
          "conversation_id": null,                    // omit to start a new conversation
          "character_slug": "abu_bakr",                // required if conversation_id is omitted
          "mode": "adults"                              // "kids" | "adults"; required if conversation_id is omitted
        }

    Continuing an existing conversation:
        {
          "message": "وماذا حدث بعد ذلك؟",
          "conversation_id": "8dfaf223-4c29-4207-8810-70b12d778fcf"
        }
        character_slug/mode are optional here:
          - if character_slug is provided and does NOT match the
            conversation's character -> streamed `error` event, 400-equivalent
          - if mode is provided and differs from what's stored, the
            conversation's mode is updated going forward (supports a
            kid/adult toggle mid-conversation)

    Response: `Content-Type: text/event-stream`, one HTTP response per
    call (not a WebSocket). Headers include Cache-Control: no-cache and
    X-Accel-Buffering: no (disables proxy buffering).

    See section 4 for the exact SSE event contract.


POST /api/v1/stt/transcribe   <-- SPEECH-TO-TEXT (voice input)
    Content-Type: multipart/form-data
    Form field: `audio` — the audio file (allowed extensions: .mp3, .mp4,
    .mpeg, .mpga, .m4a, .wav, .webm, .ogg; max size STT_MAX_AUDIO_BYTES,
    default 25 MB, matching OpenAI's own limit)

    200 -> {"text": "النص المفرَّغ من الصوت"}

    This ONLY transcribes — it does not create/continue a conversation and
    does not generate any answer. Send the returned text through
    POST /api/v1/chat/stream yourself, exactly like a typed message.

    400 -> unsupported file type / empty file / file too large

    Example:
        curl -X POST $BASE_URL/api/v1/stt/transcribe \
          -H "Authorization: Bearer $API_AUTH_TOKEN" \
          -F "audio=@recording.m4a;type=audio/m4a"


POST /api/v1/tts/speak   <-- TEXT-TO-SPEECH (voice output, SILMA on SageMaker)
    Content-Type: application/json
    Request body — exactly ONE of `text` or `message_id`:
        {"text": "النص المطلوب نطقه"}
        {"message_id": "<uuid of an existing assistant Message>"}
        optional in both: {"voice_id": "pixel"}   // overrides TTS_DEFAULT_VOICE_ID

    Inline citation markers ([1], [٢], ...) are stripped from the text
    before synthesis automatically (reads badly aloud otherwise) — the
    Flutter app does not need to strip them itself before calling this.

Synthesis uses fully-diacritized (tashkeel) Arabic text when it's
    available, to improve SILMA's pronunciation — this never changes
    `messages.content` or what any other endpoint returns; the client
    never sees diacritics. There is no LLM-based diacritizer anywhere in
    this endpoint, not even as a fallback:
      - `message_id` pointing at a grounded answer POST /api/v1/chat/
        stream generated after this feature shipped: the exact
        diacritized text the chat LLM already produced
        (`extra.diacritized_content`, see GET /api/v1/conversations/{id}
        above) is used verbatim.
      - `text`, or a `message_id` with no stored diacritized version
        (older messages, or the ungrounded-fallback answer): spoken as
        plain, undiacritized text — that's fine, not an error.

    The text (diacritized or not) is split into sentence-sized segments
    (on sentence-ending punctuation and newlines) and each is sent to
    SageMaker as its own call — SageMaker itself has no incremental/
    streaming synthesis mode, so this is what actually gets audio
    flowing early: the first sentence's audio starts streaming back
    before later sentences have even been sent to SageMaker, rather than
    one call that must finish synthesizing the entire answer first.

    200 -> `Content-Type: application/octet-stream`, streamed body of raw
    PCM audio: int16 little-endian, mono — NOT a WAV/MP3 container, just
    the raw samples (the backend receives a complete WAV file per segment
    from SageMaker and strips its header before streaming, so segment
    boundaries are invisible in the byte stream — it's all one continuous
    raw PCM stream from the client's point of view). Response headers
    describe the actual format of THIS response — always read
    X-Audio-Sample-Rate rather than assuming a fixed value, since it
    reflects whatever rate SILMA actually produced for this call, e.g.:
        X-Audio-Sample-Rate: 24000
        X-Audio-Channels: 1
        X-Audio-Sample-Format: pcm_s16le

    400 -> validation error (both/neither of text+message_id, text too
           long, nothing to synthesize after stripping citation markers)
    404 -> unknown message_id, or message_id is not an assistant message
    502 -> SageMaker responded but its audio was unusable (empty, not
           16-bit mono, or not parsable as WAV) — an upstream data
           problem, distinct from 503 below
    503 -> TTS is not configured on this deployment (SILMA_SAGEMAKER_
           ENDPOINT_NAME unset) or the SageMaker call itself failed
           (network/auth/endpoint error)

    Example:
        curl -X POST $BASE_URL/api/v1/tts/speak \
          -H "Authorization: Bearer $API_AUTH_TOKEN" \
          -H "Content-Type: application/json" \
          -d '{"message_id":"8dfaf223-4c29-4207-8810-70b12d778fcf"}' \
          --output reply.pcm


POST /api/v1/tts/speak/live   <-- TEXT-TO-SPEECH WHILE THE ANSWER IS STILL GENERATING
    Content-Type: application/json
    Request body:
        {"generation_id": "<uuid from chat/stream's 'conversation' event>"}
        optional: {"voice_id": "pixel"}

    Same response shape/headers/status codes as POST /api/v1/tts/speak
    (raw PCM, X-Audio-Sample-Rate/Channels/Sample-Format headers, 502/503
    on synthesis failure). The difference is entirely in what text it
    speaks and when it can start: this endpoint is paired, via
    generation_id, to a specific POST /api/v1/chat/stream call — call it
    immediately after receiving that call's "conversation" event, in
    PARALLEL with continuing to read the chat SSE stream, rather than
    waiting for `done`. The backend feeds this endpoint's TTS the same
    diacritized text as it's produced by the LLM, sentence by sentence
    (see app/services/tts.py's segmenting, section 10) — so the first
    sentence's audio can start reaching the client while the chat
    response is still streaming its second or third sentence as text,
    instead of waiting for the whole answer plus a round-trip through
    GET/message_id first.

    A generation_id stays valid for a few minutes after its chat/stream
    call finishes too (in case the app calls this a moment after `done`
    rather than mid-stream) — after that, or if it's simply unknown,
    this returns 404. There is no `text`/`message_id` variant of this
    endpoint; use POST /api/v1/tts/speak for those.

    400 -> validation error (missing generation_id)
    404 -> unknown or expired generation_id
    502/503 -> same meaning as POST /api/v1/tts/speak

    Example (started right after the "conversation" event arrives, while
    the chat SSE stream above is still being read):
        curl -X POST $BASE_URL/api/v1/tts/speak/live \
          -H "Authorization: Bearer $API_AUTH_TOKEN" \
          -H "Content-Type: application/json" \
          -d '{"generation_id":"3f29a1f0-2222-4444-8888-abcdef123456"}' \
          --output reply.pcm

--------------------------------------------------------------------------------
4. SERVER-SENT EVENTS (SSE) CONTRACT — POST /api/v1/chat/stream
--------------------------------------------------------------------------------

Each event is two lines followed by a blank line:

    event: <name>
    data: <JSON>
    <blank line>

Events, always in this order:

  1. "conversation"  (always first, exactly once)
        data: {"conversation_id": "<uuid>", "generation_id": "<uuid>"}
        Sent as soon as the conversation is resolved/created — capture
        this immediately so the client has it even if something fails
        later in the stream. `generation_id` identifies THIS specific
        answer's in-flight generation — pass it to POST /api/v1/tts/
        speak/live right away (in parallel with continuing to read this
        SSE stream) to start hearing the answer before it has finished
        streaming as text; see section 3.

  2. "delta"  (zero or more times)
        data: {"text": "<incremental text chunk>"}
        Concatenate all "delta" event texts in order to get the full
        response. If the question isn't covered by the retrieved
        sources, exactly ONE "delta" event is sent containing a fixed,
        honest "not enough information" message (mode-appropriate) —
        the LLM is not called in that case at all.

        Every GROUNDED answer (not the ungrounded-fallback message above,
        which stays a plain "sources don't cover this" statement with no
        invitation to keep going) ends with exactly this question,
        appended as one final "delta":
            ماذا تريد أن تعرف أيضاً عن هذه الشخصية العظيمة؟
        The client doesn't need to do anything special for this — it's
        just more streamed text — but it's always there, and it's the
        same sentence every time (guaranteed in code, not left to the
        LLM). It is deliberately excluded from what the LLM sees as its
        own prior turns in later messages (section 5) so it never gets
        echoed into the middle of a new answer. A conversation's very
        first grounded answer is also kept concise (roughly two
        paragraphs at most), and any answer to a broad, unspecific
        "tell me about this person"-style question stays brief by
        default too — see section 5.

  3. "citations"  (always exactly once, after the last "delta")
        data: {"citations": [
          {
            "index": 1,
            "book_title": "سير أعلام النبلاء - ط الرسالة",
            "author": "شمس الدين الذهبي",
            "character": "abu_bakr",
            "character_name": "أبو بكر الصديق",
            "page": "46",
            "source_url": "https://read.shamela.ws/book/10906/1194",
            "score": 0.457
          },
          ...
        ]}
        Empty array [] when the ungrounded fallback was used. The
        assistant's streamed text references these by their "index"
        inline as [1], [2], etc. (Arabic-Indic digits — ١، ٢، ٣...) —
        the Flutter UI can render these as tappable citation markers
        linking to source_url.

  4. "suggestions"  (always exactly once, after "citations")
        data: {"suggestions": ["سؤال متابعة أول؟", "سؤال متابعة ثانٍ؟"]}
        0 to 3 short Arabic follow-up questions. Up to 2 are predefined
        (fixed, chosen deterministically by NarratorMode and, for
        "adults", the character's role — see section 5) and cost no LLM
        call; any remaining slot (0 or 1 in practice) is filled by the
        LLM deciding whether a natural follow-up exists, same as before.
        A suggestion the user has already sent as a message earlier in
        this same conversation is never shown again — predefined or
        LLM-generated — for the rest of that conversation. Always [] for
        the ungrounded-fallback case (no LLM call is made for that turn
        at all, including for suggestions — this is unchanged; predefined
        suggestions are currently only shown for grounded answers).

  5. "done"  (always exactly once, terminal)
        data: {}

  OR, at any point instead of the above: "error" (terminal)
        data: {"message": "<human-readable error>"}
        Sent for validation failures (e.g. missing character_slug on a
        new conversation, unknown character, unknown conversation_id,
        mismatched character_slug) or unexpected failures (LLM/DB
        errors). No further events follow an "error".

Persistence timing: the user's message is saved immediately (survives
even if generation fails); the assistant's message + citations + any
suggestions are saved only after the stream completes successfully — a
failed/interrupted generation never leaves a partial/bogus assistant turn
in history. Suggestions are stored in that message's `extra` field
(`{"suggestions": [...]}`) and returned by GET /api/v1/conversations/{id}.

5. CONVERSATIONAL CONTINUITY & GROUNDING (how it actually works)
--------------------------------------------------------------------------------

- The client only needs to remember `conversation_id` (a UUID) — never the
  full message history. On each new message, the backend loads the last
  HISTORY_MAX_MESSAGES (default 8) turns from Postgres itself and includes
  them as real prior turns in the LLM's message list.

- Retrieval query augmentation: a short follow-up like "وماذا حدث بعد
  ذلك؟" ("what happened next?") carries almost no topical signal on its
  own and retrieves poorly in isolation. The backend folds the previous
  user turn into the text used for embedding/retrieval (not into what's
  shown to the LLM as "the question", which stays the literal current
  message) — this measurably fixes follow-up retrieval without an extra
  LLM call to rewrite the query.

- Grounding gate: retrieval runs with RETRIEVAL_TOP_K chunks (default 5).
  If zero chunks come back, OR the best (top) result's cosine-similarity
  score is below RETRIEVAL_MIN_SCORE (default 0.28, calibrated against
  real data — see Limitations), the LLM is skipped entirely and a fixed,
  mode-appropriate "sources don't cover this" message is returned. This
  is a hard, deterministic backstop — the system prompt sent to the LLM
  additionally instructs it (as defense in depth) to say so itself if the
  attached sources are insufficient, and to never invent facts, names, or
  dates beyond them.

- The narrator never speaks as the historical figure in first person —
  the system prompt (rag/generation/prompt.py, narrator_system_prompt())
  explicitly forbids this and requires third-person narration, in both
  "kids" (simple, warm, values/lessons-focused Arabic) and "adults"
  (sophisticated Arabic with historical/political/social context) modes.

- A conversation's very first grounded answer is instructed to stay
  concise (roughly two paragraphs at most) — later answers go back to the
  normal question-driven length (a simple factual question still gets a
  short answer; an explicit request for a detailed story can be longer).
  Every answer, first or not, ends with the exact same fixed closing
  question (see the "delta" event above) — appended in code after the
  LLM's own text finishes streaming, not left to the LLM to phrase.

- Suggestions (app/services/suggestions.py) are up to 2 predefined + LLM
  top-up, not 100% LLM-decided like before:
    - Predefined suggestions are chosen purely by NarratorMode (never raw
      age — the Flutter app already converts age to "kids"/"adults",
      which is the only signal used here) and cost no LLM call:
        - "kids": always the same fixed 2 questions.
        - "adults": always the same fixed first question, plus a second
          question fixed per the character's role/category (e.g. "قائد
          عسكري" gets a different fixed question than "عالم") — chosen
          deterministically when a character has more than one category
          by a fixed priority order over the whole role taxonomy. If the
          character has no matching role (e.g. not yet classified — see
          docs/RAG.md or scripts/generate_character_classification.py),
          only the first fixed question is shown.
    - Once a suggestion (predefined or not) has been sent by the user as
      an actual message anywhere earlier in the SAME conversation, it is
      permanently excluded from that conversation's future suggestion
      lists — this is checked against every user message ever sent in
      the conversation, not just the recent history window.
    - Any slot left after predefined suggestions (0, 1, or up to all 3 if
      predefined ones were already used) is filled by the same
      LLM-decides-whether-it's-useful call as before (rag/generation/
      prompt.py build_suggestions_prompt(), JSON response mode, explicitly
      told which questions are already used so it doesn't repeat them,
      even paraphrased) — it can still return fewer than the available
      slots, or none. This adds a small tail latency after the "delta"
      events stop and before "citations"/"suggestions" arrive — expected
      and intentional (see Limitations). Any failure in this step (API
      error, malformed JSON) falls back to the predefined suggestions
      alone; it never breaks the main answer, which is already fully
      streamed and saved by that point.

6. HOW TO RUN THE BACKEND LOCALLY
--------------------------------------------------------------------------------

Prerequisites: Postgres with the `vector` extension enabled (see
docs/RAG.md section "Setup" — docker-compose or a native install both
work).

    pip install -r requirements.txt
    cp .env.example .env         # fill in DATABASE_URL, OPENAI_API_KEY, API_AUTH_TOKEN
    alembic upgrade head          # creates + seeds characters (+ categories taxonomy),
                                   # conversations, messages, story_of_day
    uvicorn app.main:app --reload --port 8000

You do NOT need to run ingestion manually first: on every startup the
backend automatically ingests, in a background thread, any character
present under RAG_DATA_DIR (default data/raw/*) that isn't in the DB yet
(see docs/RAG.md "Automatic ingestion on backend startup"). GET /health
and every other route respond immediately regardless of how long that
takes — the API never waits on it. Set AUTO_INGEST_ON_STARTUP=false to
disable this (e.g. a scaled-out instance that shouldn't also ingest).
To force a character to be re-ingested (e.g. corrected source text),
delete it first: `python -m rag.ingestion.delete_character <character_id>`
— the next startup (or manual ingestion run) will pick it up as missing.

A character's `categories` (role taxonomy) and `short_description` are NOT
part of this automatic ingestion/seeding — they go through a separate,
three-step pipeline, and only the last step runs on a server:

  1. Locally, with OPENAI_API_KEY set: `scripts/generate_character_
     classification.py submit`, then once the OpenAI Batch job completes,
     `... apply --batch-id <id>` — writes categories/short_description
     into YOUR local DB and an audit JSONL, same as before.
  2. Locally: `python -m scripts.export_character_classifications` —
     snapshots every character's current categories/short_description
     from that DB into data/generated/character_classifications.json.
     Commit this file.
  3. On a server (or anywhere else): nothing to run manually. On every
     backend startup, app.services.character_classification_sync reads
     that committed file and applies it to whatever DB it's running
     against (only the rows that actually differ) — see AUTO_SYNC_
     CLASSIFICATIONS_ON_STARTUP below. No OPENAI_API_KEY, no Batch job,
     and no scripts/ directory are needed on a server for this.

`era`/`group` are unaffected by any of this and are only ever set by data
seeding/migrations.

Interactive API docs (Swagger UI): http://127.0.0.1:8000/docs
(the auth padlock in that UI accepts your API_AUTH_TOKEN as a Bearer token)

Docker (no local Python needed): `docker compose up --build` runs both
`db` and `api` services (see docker-compose.yml). Run `alembic upgrade
head` once against the compose Postgres before first use.

TTS is optional at boot: if SILMA_SAGEMAKER_ENDPOINT_NAME is unset, every
endpoint except POST /api/v1/tts/speak works normally; that one endpoint
returns a clear 503 until it's configured (see section 8).

7. HOW TO TEST THE MAIN CHAT FLOW (AND VOICE I/O)
--------------------------------------------------------------------------------

Automated (no real OpenAI/AWS calls — uses tests/fake_embedder.py,
tests/fake_llm.py, tests/fake_stt.py, tests/fake_tts.py):

    pytest tests/
    (100+ tests as of this writing: RAG pipeline tests + API tests
    covering auth, character/story listing, the grounded/ungrounded chat
    paths, conversation persistence, follow-up context handling,
    LLM-decided suggestions, speech-to-text, and text-to-speech
    including sentence-segmented and live/mid-generation synthesis.)

Manual, against a real running server + real OpenAI (uses your real
OPENAI_API_KEY and calls the actual embeddings + chat completion +
transcription APIs):

    curl -s http://127.0.0.1:8000/api/v1/characters \
      -H "Authorization: Bearer $API_AUTH_TOKEN"

    curl -N -X POST http://127.0.0.1:8000/api/v1/chat/stream \
      -H "Authorization: Bearer $API_AUTH_TOKEN" \
      -H "Content-Type: application/json" \
      -d '{"message":"كيف تولى أبو بكر الخلافة؟","character_slug":"abu_bakr","mode":"adults"}'

    (-N disables curl's output buffering so you see SSE events arrive live.
    On Windows, prefer writing the JSON body to a file and using
    `--data-binary @file.json` — passing Arabic text through shell
    argument quoting can silently corrupt the UTF-8 bytes and produce
    misleadingly low retrieval scores; this bit us during development,
    see Limitations.)

    Then GET /api/v1/conversations/<conversation_id from the stream> to
    confirm the turn (and any suggestions, in `extra`) was persisted
    correctly.

    Speech-to-text (real OpenAI call):
        curl -X POST http://127.0.0.1:8000/api/v1/stt/transcribe \
          -H "Authorization: Bearer $API_AUTH_TOKEN" \
          -F "audio=@recording.wav;type=audio/wav"
    This was verified end-to-end during development using a synthesized
    speech WAV file — the returned text matched the spoken audio.

    Text-to-speech: requires SILMA_SAGEMAKER_ENDPOINT_NAME + AWS
    credentials to be configured (see section 8) — none were available in
    the environment this backend was built in, so this endpoint's
    happy path is verified only by the fake-backed automated tests plus a
    manual check that it fails clearly (503, actionable message) when
    unconfigured, not by a real SageMaker call. Once credentials exist:
        curl -X POST http://127.0.0.1:8000/api/v1/tts/speak \
          -H "Authorization: Bearer $API_AUTH_TOKEN" \
          -H "Content-Type: application/json" \
          -d '{"text":"مرحبا"}' --output out.pcm
    Play out.pcm as raw PCM (int16 LE, mono, 32000 Hz), e.g.:
        ffplay -f s16le -ar 32000 -ac 1 out.pcm

9. HOW FLUTTER SHOULD CONSUME THE STREAMING CHAT API
--------------------------------------------------------------------------------

This is plain HTTP with a `text/event-stream` body over a POST request —
NOT the browser `EventSource` API (which can't do POST/custom headers
anyway) and not a WebSocket. Use Dart's `http.Client` in streamed mode:

    import 'dart:convert';
    import 'package:http/http.dart' as http;

    final client = http.Client();
    final request = http.Request(
      'POST',
      Uri.parse('$baseUrl/api/v1/chat/stream'),
    )
      ..headers['Authorization'] = 'Bearer $apiAuthToken'
      ..headers['Content-Type'] = 'application/json'
      ..body = jsonEncode({
        'message': userMessage,
        if (conversationId != null) 'conversation_id': conversationId,
        if (conversationId == null) 'character_slug': selectedCharacterSlug,
        if (conversationId == null) 'mode': narratorMode, // 'kids' | 'adults'
      });

    final response = await client.send(request);
    final stream = response.stream.transform(utf8.decoder);

    String buffer = '';
    await for (final chunk in stream) {
      buffer += chunk;
      // SSE events are separated by a blank line ("\n\n")
      while (buffer.contains('\n\n')) {
        final idx = buffer.indexOf('\n\n');
        final rawEvent = buffer.substring(0, idx);
        buffer = buffer.substring(idx + 2);

        final lines = rawEvent.split('\n');
        final eventName = lines[0].replaceFirst('event: ', '');
        final data = jsonDecode(lines[1].replaceFirst('data: ', ''));

        switch (eventName) {
          case 'conversation':
            conversationId = data['conversation_id'];
            break;
          case 'delta':
            appendToNarratorBubble(data['text']);
            break;
          case 'citations':
            showCitations(data['citations']); // list of {index, book_title, author, ...}
            break;
          case 'suggestions':
            // data['suggestions'] is a list of 0-3 Arabic strings — only
            // show a "suggested questions" row/chips when it's non-empty;
            // an empty list is the normal case, not an error.
            showSuggestedQuestions(data['suggestions']);
            break;
          case 'done':
            markResponseComplete();
            break;
          case 'error':
            showErrorToUser(data['message']);
            break;
        }
      }
    }

Notes for the Flutter integration:
  - Persist `conversation_id` locally (e.g. shared_preferences) per
    character chat, and pass it on every subsequent message for that
    conversation — no need to resend prior messages.
  - On app restart, if you want to show prior turns, call
    GET /api/v1/conversations/{conversation_id} once to rehydrate the UI
    (each stored assistant message's `extra.suggestions`, if present, can
    repopulate that turn's suggestion chips too).
  - Render citation markers ([1], [2]...) in the streamed text as tappable
    chips using the matching entry from the "citations" event's array
    (open source_url in an in-app browser / external link).
  - Tapping a suggestion chip is just a normal next chat message: send it
    as `message` with the same `conversation_id` — no special endpoint.
  - `generation_id` (from the "conversation" event) is per-turn and
    short-lived — unlike `conversation_id`, don't persist it; it's only
    good for calling POST /api/v1/tts/speak/live for that one answer,
    for a few minutes after that answer finishes streaming.
  - A package like `flutter_client_sse` can also parse this exact format
    if preferred over hand-rolling the buffer/split logic above — the
    event names and payloads above are what it needs to match.

VOICE INPUT (speech-to-text) — plain JSON request/response, no streaming:

    import 'package:http/http.dart' as http;

    final request = http.MultipartRequest(
      'POST',
      Uri.parse('$baseUrl/api/v1/stt/transcribe'),
    )
      ..headers['Authorization'] = 'Bearer $apiAuthToken'
      ..files.add(await http.MultipartFile.fromPath('audio', recordedFilePath));

    final streamedResponse = await request.send();
    final response = await http.Response.fromStream(streamedResponse);
    final text = jsonDecode(response.body)['text'] as String;
    // Now send `text` through POST /api/v1/chat/stream like any typed
    // message — this endpoint does NOT generate an answer itself.

VOICE OUTPUT (text-to-speech) — the response body is raw PCM audio
(int16 little-endian, mono — NOT a WAV/MP3 file; sample rate varies per
call, see below), and the backend itself streams it incrementally (first
sentence's audio before later sentences are even synthesized — see
section 10), so the client should consume it as a stream too, not wait
for `bodyBytes` to buffer the whole thing before playing anything:

    final request = http.Request(
      'POST',
      Uri.parse('$baseUrl/api/v1/tts/speak'),
    )
      ..headers['Authorization'] = 'Bearer $apiAuthToken'
      ..headers['Content-Type'] = 'application/json'
      ..body = jsonEncode({'message_id': assistantMessageId});

    final response = await client.send(request);
    final sampleRate = int.parse(response.headers['x-audio-sample-rate']!);
    // headers also include x-audio-channels, x-audio-sample-format --
    // read these rather than hardcoding a fixed rate/format, since they
    // reflect whatever this specific call's audio actually is.

    await for (final chunk in response.stream) {
      // Feed each raw-byte chunk to a raw-PCM player as it arrives, e.g.
      // the `flutter_pcm_sound` package configured with sampleRate /
      // mono / 16-bit signed samples -- don't accumulate the whole
      // response first, that throws away the backend's streaming.
      pcmPlayer.feed(chunk);
    }

To start hearing an answer before it has finished streaming as text, use
POST /api/v1/tts/speak/live instead of /speak, called with the
generation_id from the "conversation" SSE event (section 4) — fire it as
soon as that event arrives, in parallel with continuing to read the chat
stream above, not after `done`. Everything else (headers, streamed body,
player wiring) is identical to the /speak example above; only the
request body differs:

    body: jsonEncode({'generation_id': generationId})

10. IMPORTANT DECISIONS & LIMITATIONS
--------------------------------------------------------------------------------

- No user-account system yet. A conversation is identified only by its
  UUID; anyone holding the shared API_AUTH_TOKEN and a conversation_id can
  read/continue it. Acceptable for an MVP single-shared-secret mobile
  backend; should be revisited (real per-user auth + conversation
  ownership) before wider release.

- No distributed rate limiting. The bearer token plus per-message length
  cap (MAX_MESSAGE_LENGTH) are the only abuse guards. For production,
  add rate limiting at the AWS layer (API Gateway / ALB / WAF) rather
  than in-process (in-process counters don't work correctly once the
  service scales to multiple instances).

- RETRIEVAL_MIN_SCORE=0.28 was calibrated empirically against this
  dataset/embedding model: off-topic questions ("best pizza recipe",
  "who won the 2022 World Cup") scored 0.08-0.18 top similarity; genuine
  on-topic questions scored 0.40-0.55. 0.28 sits in the gap with margin
  on both sides. This should be re-validated if the embedding model or
  corpus changes materially.

- Citation numbering ([1], [2]...) is per-turn, based on that turn's
  freshly retrieved sources. If the LLM references [1] inside history
  text from a prior turn, that number reflects the prior turn's source
  list, not the current one — a minor, inherent limitation of any
  inline-citation-in-text scheme combined with a sliding retrieval window.
  The structured "citations" event for the CURRENT turn is always
  authoritative for that turn's answer.

- Dockerfile/docker-compose `api` service were written but not build-
  tested in this environment (no Docker available here) — the image
  layout is straightforward (single pip install + uvicorn CMD) but
  should be verified once Docker/AWS access is available.

- Story-of-day's non-curated fallback is a stateless date-hash rotation
  (no admin UI to curate a specific date exists yet) — inserting a row
  into `story_of_day` directly (or via a future admin endpoint) overrides
  it for that date.

- `messages.extra` (JSONB) currently holds `suggestions` (if any) and, for
  grounded answers, `diacritized_content` (the same answer with tashkeel,
  used only by POST /api/v1/tts/speak — see section 3); otherwise it's a
  deliberate forward-compatibility seam for future interactive story
  choices/branching — no schema migration should be needed to add more.

- Suggestions add one extra, non-streamed LLM call per grounded answer,
  made AFTER the narrative text finishes streaming — so there's a small
  extra tail latency (typically ~1 second) between the last "delta" event
  and the "citations"/"suggestions"/"done" events. This was a deliberate
  trade-off for correctness/simplicity (a real LLM judgment call via
  JSON mode) over trying to parse structured suggestions out of the
  middle of a token stream. No suggestions call happens at all for the
  ungrounded-fallback path.

- TTS (POST /api/v1/tts/speak) is now deployed and live against a real
  SILMA SageMaker endpoint. Its actual inference.py returns JSON —
  {"audio_base64": <a complete WAV file>, "format": "wav", "sample_rate":
  <int>} — regardless of any Accept header sent, not headerless raw PCM
  at a fixed rate as an earlier reference implementation assumed.
  app/services/tts.py decodes that WAV file and strips its header before
  streaming, and reads sample_rate/channels/sample_width from the WAV's
  own fmt chunk (authoritative over the JSON's sample_rate field) rather
  than assuming any fixed value — 16-bit mono is required; anything else
  fails clearly with 502 rather than being mislabeled and streamed
  anyway. Getting this wrong (streaming the WAV file's header, or the raw
  JSON bytes, straight through as if already headerless PCM) is what
  previously produced static/noise instead of speech on the client.

- TTS synthesizes sentence-by-sentence (app/services/tts.py), not the
  whole answer as one SageMaker call. SageMaker has no incremental
  synthesis mode of its own — a single call always processes its entire
  input before returning any audio — so for a long answer, splitting
  into segments and streaming each one's audio as soon as it's ready is
  what actually gets sound to the client quickly, instead of a long
  silent wait for one big call to finish. `TextToSpeech.speak()` takes an
  async *stream* of text (not a single string) specifically so this
  works whether the caller already has the complete text (today's only
  caller, POST /api/v1/tts/speak, wraps it as a one-shot stream) or a
  genuinely live source arriving incrementally — piping live chat-
  generation tokens straight into TTS as they stream would need no
  further changes to this module, only new wiring at the call site,
  which does not exist yet.

- POST /api/v1/tts/speak/live works by fanning out the same diacritized
  tokens app/api/routes/chat.py is already producing (for `extra.
  diacritized_content`) to a second, concurrent HTTP request in memory
  (app/services/live_generation.py) — no extra LLM call, no polling. This
  is plain in-process state: it assumes one instance handles both the
  chat/stream and the matching speak/live request, same simplifying
  assumption already made by the module-level SageMaker client/lock in
  app/services/tts.py. It has not been load-tested across multiple
  worker processes/instances and would need sticky routing (or a shared
  broker) before scaling out to more than one.

- There is no LLM-based diacritizer anywhere in TTS, including as a
  fallback. Diacritics only ever come from the chat LLM writing them
  itself (rag/generation/prompt.py DIACRITIZATION_RULE); any text with no
  pre-existing diacritics (arbitrary `text` requests, older messages, the
  ungrounded-fallback answer) is simply synthesized without them — a
  deliberate simplicity/latency trade-off, not a bug.

- STT (POST /api/v1/stt/transcribe) WAS verified end-to-end against the
  real OpenAI API during development (a synthesized speech WAV file
  transcribed correctly).

- The raw-PCM audio format for TTS (no WAV/MP3 container) is a contract
  this backend enforces itself — SageMaker's actual response is a
  complete WAV file; the backend strips its header so downstream clients
  never need to (see above). The Flutter app needs a raw-PCM-capable
  audio player (see section 9) rather than a standard file-based one, and
  should read X-Audio-Sample-Rate per response rather than hardcoding a
  value, since it varies by call.
